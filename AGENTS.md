# Santa Social project instructions

- Use JavaScript throughout the authored application. React components, layouts and pages must use `.jsx`; application logic, utilities, backend modules and tests must use `.js`.
- Keep Next.js App Router and the Express API modules. Production single-subdomain hosting uses the root `server.js` custom server to serve pages/assets and `/api/*` on one managed port. Separate development/API startup remains available. Do not introduce Vite, TypeScript syntax, `.ts`/`.tsx` source, TypeScript declarations, `tsconfig.json`, or a TypeScript runtime/build dependency.
- Next.js configuration uses `frontend/next.config.mjs`. Existing tooling configuration/scripts may use `.mjs` or `.cjs` where required by their module format.
- Preserve `frontend/jsconfig.json`'s `@/*` alias. The backend is native Node.js ESM and uses explicit `.js` extensions on relative imports. It runs directly from `backend/src/`, including in production.
- Keep runtime Zod validation, database schema, endpoint contracts, server-verified captured payments, secure receipt links, cash approval, OTP restrictions and atomic entry intact.
- Provider simulation and storage are independent: `APP_MODE=demo` may use `DB_DRIVER=mysql`. Hosted prototypes and live deployments require MySQL; SQLite is only a local development/test adapter. Keep AskEva, Razorpay and SMTP simulated in the hosted prototype and preserve the explicit production demo opt-in and strong secrets/staff credentials.
- The owner authorizes real Razorpay payments with simulated OTP/notifications. `PAYMENT_MODE=live` independently enables Razorpay order creation, verification, webhooks and reconciliation; `APP_MODE=demo` retains simulated AskEva/SMTP. Require Live Razorpay credentials, a separate webhook secret and MySQL. The demo completion endpoint must be disabled whenever payments are live. Never accept an old simulated online payment/QR as paid admission in live payment mode.
- Do not manually edit generated `.next` files or dependency source. Retain the framework-managed guidance in `frontend/AGENTS.md`.
- Run `npm run check`, `npm test`, and `npm run build` after substantive changes. Use the existing browser QA for customer/staff workflow changes. Report unavailable external integration or MySQL verification honestly.
- `/` is the direct booking landing page; `/register` is a legacy redirect. Preserve the existing registration UI and do not restore the promotional homepage. Public registration QR assets use only the actual configured deployed HTTPS URL and remain separate from per-booking admission QR tokens; never generate final assets for localhost, private addresses or sample domains.
- Registration mobile OTP verification belongs inline in the WhatsApp field on `/`. Keep only Your booking and Checkout in the progress bar; `/verify-otp` is a legacy redirect to `/`. Require a matching server-verified mobile session before checkout or booking creation. Changing a number or losing that session must invalidate the verified indicator. Preserve the separate secure ticket-retrieval verification flow.
- Staff share `/login`; legacy admin/scanner login paths redirect there. An admin session authorizes all staff modules including scanner; retain cashier/scanner role restrictions. Return paths after login must stay inside authorized staff routes. The hosted prototype requires only admin credentials; limited staff account pairs are optional.
- Fresh document visits, reloads and new tabs for admin/scanner show Admin Login even if a staff cookie exists. Keep the successful-login UI grant in memory only, shared across client navigation between modules; server cookies and role checks remain the authorization authority.
- Staff and customers must use separate cookies (`santa_staff_session` and `santa_session`) and explicit identity scopes in frontend session checks. Customer OTP must not replace staff permissions. Keep legacy staff-cookie migration, independent logout, and backend role/ownership enforcement. Failed admin data loads must stop the spinner and offer retry.
- New cash reservations receive individual QR tickets immediately, but it authorizes lookup only until payment approval. Scanner results show unpaid cash in red and paid bookings in green. Only an admin may collect exact cash and approve only the scanned individual ticket atomically from the scanner; scanner-only staff cannot collect cash. Keep the same QR after approval, event-date checks and single-entry protection.
- Registrations have no total/daily attendance cap or payment deadline. Legacy capacity/hold database columns remain for compatibility but must not reject registrations, expire pending bookings, or appear as customer deadlines. Keep group-size, OTP/session expiry, captured-payment, cancellation and event-date protections.
- Successful online payment opens `/ticket/:id` directly after server-confirmed PAID/FREE status; never route pending capture or callback-only success to an admission QR. Failed/cancelled payments show a retryable error on checkout. Keep demo payments explicitly labelled and simulated until the owner configures a payment provider.
- Cash and online tickets share the existing branded card. PDF, saved PNG and shared image files must include the complete red header, original brand logo, booking details and original QR. Keep unpaid cash clearly marked due/approval required. Downloads require owner/staff authorization or a valid ticket bearer; never expose tickets by booking ID alone.

- AskEVA WhatsApp delivery is independent: `WHATSAPP_MODE=live` enables the built-in documented template adapter while `APP_MODE=demo` can retain simulated SMTP and `PAYMENT_MODE=live` retains real Razorpay. Live WhatsApp requires MySQL, strong secrets and ASKEVA_API_KEY; never return demo OTP codes in live WhatsApp mode. Keep the five-minute OTP lifetime and secure bearer ticket links. See docs/ASKEVA-SETUP.md.

- New bookings use individual_tickets and ticket_batches: one independent secure QR per adult/child, with atomic approval, partial entry and one secure receipt link per booking. Existing bookings without a batch remain legacy group tickets; never automatically convert their entry history. PDF includes all individual tickets; PNG/share image includes the selected ticket. Preserve per-ticket approval timestamps/admins and server IST date validation.
