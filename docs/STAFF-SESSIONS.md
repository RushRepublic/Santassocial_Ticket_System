# Persistent staff authentication

Staff authenticate through the existing `/api/auth/login` route. Each successful login issues a newly signed JWT with a random `jti`, an original `iat` and a fixed `exp = iat + 86400` seconds. The separate `santa_staff_session` cookie is HttpOnly, SameSite=Lax, Path=/api, Max-Age=86400 and Secure in production. No passwords or authentication tokens are stored in JavaScript storage.

Dashboard and scanner restore their identity through `/api/auth/me?scope=staff` before displaying protected content. Page loads, API calls and scans never renew the token or cookie. Backend signature, expiration, active-account and role checks remain mandatory on every request. The frontend uses the server's remaining lifetime for its expiration check, plus focus/visibility checks and a 30-second validation interval. The API rejects expired sessions immediately, even before the next frontend check.

Logout writes a SHA-256 token hash to `revoked_staff_sessions` before clearing the cookie. This persists across process restarts and blocks replay of the same JWT. A BroadcastChannel logout notice clears other open staff views; browsers without BroadcastChannel revalidate on focus or the next periodic/API check. Customer authentication remains independent. Existing Origin-based CSRF protection remains enabled.

Deployment adds only `revoked_staff_sessions(tokenHash, expiresAt)`. Startup creates this table safely with CREATE TABLE IF NOT EXISTS in both demo and live application modes; the normal database migration also includes it. No customer, user, booking, payment or ticket records are changed. The database account needs CREATE TABLE permission, as for the existing migrations. Missing database permissions must be resolved before deployment. Legacy signed staff cookies retain their original shorter expiry and are never extended; new successful logins receive 24 hours.

Validation: `npm run check`, `npm test`, `npm run build`; `node scripts/persistent-session-qa.mjs` against an isolated local server with demo providers. JWT boundary tests use controlled verification times, never the production clock. The browser QA restarts Chromium using a local persistent profile to verify cookie restoration. Safari/Firefox/physical mobile browser restart and production MySQL behavior require external verification. Browsers configured to delete cookies on exit cannot retain login.
